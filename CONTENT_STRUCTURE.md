# Content Structure — website

This document defines what the site needs to communicate. It intentionally avoids final copywriting.

## 1. Opening

### Must communicate

- who built the site / Station
- that the viewer is looking at a real finished product
- that the site itself is an authored interactive experience

### Avoid

- long biography
- generic "passionate developer" language
- a wall of technology badges
- explaining Station before the viewer has had time to look at it

## 2. Station overview

Keep this concise.

Useful facts may include:

- browser-based music workstation
- sampling, synthesis, sequencing, mixing and project workflow in one system
- built as a real usable product rather than a static demo

The exact feature list should not dominate the opening.

## 3. LASER chapter

### Explain

- the sampling / slicing idea in Station
- why direct manipulation matters
- what the LASER workflow adds to the product

### Show

- selected final UI
- slicing markers / waveform logic
- the website's decomposition interaction

## 4. PADS chapter

### Explain

- tactile interaction goals
- touch / pointer behavior
- pad response and physical-feel iteration
- any relevant recording / triggering workflow

### Show

- final pads
- interaction states if they are visually useful
- selective before/after examples only when they teach something

## 5. SYNTH chapter

### Explain

- that Station contains substantial synthesis capability beyond sampling
- browser audio as an implementation medium
- custom musical controls and instrument-specific design

### Show

- ZOLA-X as a major example
- selected additional synth/instrument systems if they strengthen the story
- waveform / wavetable / modulation visuals with purpose

Do not turn this chapter into a catalog of every parameter.

## 6. SEQ / SONG chapter

### Explain

- how independent musical parts become an organized composition/workflow
- sequencing, patterns, song structure or hierarchy
- how product state and timing connect previously separate systems

### Show

- the visual rebuilding of hierarchy
- selected sequencer/song views

## 7. MIX chapter

### Explain

- product judgment
- iteration
- reducing complexity
- changing direction after implementation
- willingness to remove work

### Candidate examples

- STRINGS removed
- autotune removed
- GRAVITY renamed/reverted to SIDECHAIN for clarity
- UI concepts rejected or rebuilt when they looked too dashboard-like or visually inconsistent

Before publishing, verify dates/names/final state against Station history.

### Show

- recovered earlier Station screenshots
- a small number of meaningful stages
- mixer-inspired decision metaphor

Avoid a giant chronological dump.

## 8. MASTER chapter

### Explain

- what the final Station became
- what is now stable / complete enough to present
- concise summary of the product's scope

### Calls to action

- live Station
- GitHub / source

## 9. Technical credibility

Technical detail can be distributed across the story rather than isolated in a giant "Tech Stack" block.

Potential details:

- Web Audio
- modern frontend architecture
- persistent project storage
- touch/gesture behavior
- responsive UI
- performance constraints
- testing / iterative release work
- deployment

Only include details that reinforce a concrete problem or decision.

## 10. AI-assisted workflow

This should be framed clearly and without pretending that code agents are irrelevant.

Communicate that AI agents are implementation tools inside a human-directed workflow involving:

- product decisions
- architecture
- specification
- review
- testing
- iteration
- rejection and revision

Avoid presenting agent output as autonomous product creation.

## 11. Other work

SkateRoad can be a concise secondary proof of range.

Show:

- one strong visual
- short description
- official link
- itch.io link

Do not give it equal visual weight to Station unless the project changes substantially later.

## 12. About / identity

Do not require a conventional large About section.

The site should reveal the builder through the work itself. A short personal summary near the end is enough if needed.

## 13. Contact

Make contact information obvious and low-friction.

Potential routes:

- email
- GitHub
- relevant professional profile if used

No elaborate interaction should stand between the viewer and contact details.
